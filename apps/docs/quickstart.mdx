This walkthrough uses the `shugo` CLI, not the SDK — it's the fastest way to see the whole system work end to end, no code required. For wiring Shugo into an agent framework programmatically, see the [SDK Reference](/sdk-reference) once you understand the flow here.

<Note>
  Every command and every piece of example output on this page is copied from an actual run against live Solana devnet, not written to look plausible. Your addresses and signatures will differ; the shape of the output won't.
</Note>

## Prerequisites

- Node.js 18+ and [pnpm](https://pnpm.io)
- The [Solana CLI](https://docs.anza.xyz/cli/install) tools (`solana`, `solana-keygen`, `spl-token`)
- A devnet RPC endpoint. The public `api.devnet.solana.com` rate-limits aggressively under real use — a free endpoint from [Helius](https://dashboard.helius.dev), QuickNode, or similar is strongly recommended.

## 1. Install the CLI

```bash
git clone https://github.com/shugo-protocol/shugo.git
cd shugo
pnpm install
pnpm --filter @shugo/sdk run build   # the CLI imports the SDK at runtime, so build it first
pnpm --filter @shugo/cli run build
```

<Note>
  If `pnpm install` reports ignored build scripts, approve `esbuild` with `pnpm approve-builds` — the CLI and SDK builds use it. The other packages it lists (`bufferutil`, `utf-8-validate`) are optional native speedups and can stay denied.
</Note>

## 2. Set up three identities

Shugo separates three roles on purpose: the **human** who owns the policy and funds pulls, the **agent** who is the only signer allowed to call `pull`, and a **merchant** who receives funds. Keeping agent and merchant separate is what makes the destination allowlist demonstrable — an agent that can only pay a pre-approved merchant can't redirect funds anywhere else, even if it's compromised.

```bash
solana-keygen new --outfile ~/.config/solana/human.json --no-bip39-passphrase
solana-keygen new --outfile ~/.config/solana/agent.json --no-bip39-passphrase
solana-keygen new --outfile ~/.config/solana/merchant.json --no-bip39-passphrase

export RPC="<your devnet RPC URL>"
solana airdrop 2 $(solana-keygen pubkey ~/.config/solana/human.json) --url "$RPC"
solana airdrop 1 $(solana-keygen pubkey ~/.config/solana/agent.json) --url "$RPC"
```

## 3. Create a test token

```bash
solana config set --keypair ~/.config/solana/human.json --url "$RPC"
spl-token create-token --decimals 6
# → Address: <MINT>

export MINT="<the mint address printed above>"
spl-token create-account $MINT
spl-token mint $MINT 1000

export AGENT=$(solana-keygen pubkey ~/.config/solana/agent.json)
spl-token create-account $MINT \
  --owner $(solana-keygen pubkey ~/.config/solana/merchant.json) \
  --fee-payer ~/.config/solana/human.json
# → Creating account <MERCHANT_ATA>
export MERCHANT_ATA="<that address>"
```

## 4. Create the policy

This single command does three things in one transaction: initializes the human's S&A `SubscriptionAuthority` for this mint (if one doesn't already exist), creates the Shugo Policy, and creates the real S&A `FixedDelegation` naming the policy as `delegatee`.

```bash
cd packages/cli
node dist/index.js create-policy \
  --keypair ~/.config/solana/human.json \
  --url "$RPC" \
  --mint $MINT \
  --agent $AGENT \
  --per-call-cap 50 \
  --velocity-cap 200 \
  --velocity-window-seconds 3600 \
  --destinations $MERCHANT_ATA \
  --delegation-amount 500 \
  --delegation-expiry-days 30
```


## 6. Pull funds — as the agent

This is the command the agent actually runs. Note the keypair: it's the **agent's**, not the human's.

```bash
node dist/index.js pull \
  --keypair ~/.config/solana/agent.json \
  --url "$RPC" \
  --policy $POLICY \
  --delegation $DELEGATION \
  --amount 25 \
  --destination $MERCHANT_ATA
```

```text Example output

```

## 7. The kill switch

One instruction pauses the policy — every future pull is denied immediately, regardless of amount or destination.

```bash
node dist/index.js pause --keypair ~/.config/solana/human.json --url "$RPC" --policy $POLICY

# Try to pull while paused:
node dist/index.js pull \
  --keypair ~/.config/solana/agent.json --url "$RPC" \
  --policy $POLICY --delegation $DELEGATION \
  --amount 10 --destination $MERCHANT_ATA
```

```text Example output (the pull is rejected)
Error: Simulation failed.
Message: Transaction simulation failed: Error processing Instruction 0: custom program error: 0x1770.
Logs:
[
  "Program 6gHABW3Rn5dsTdXKN2xzRdb4g9v2DjYmc9sKq1Wn8my9 invoke [1]",
  "Program log: Instruction: ExecutePull",
  "Program log: AnchorError occurred. Error Code: Paused. Error Number: 6000. Error Message: This policy is paused.",
  ...

```

```bash
node dist/index.js resume --keypair ~/.config/solana/human.json --url "$RPC" --policy $POLICY
```

## What you just proved

The agent could only ever pay `$MERCHANT_ATA` — a different destination would be denied the same way the paused pull was, by `execute_pull`'s own checks, before any CPI into S&A happens. Try it: build a second token account for an address that isn't `$MERCHANT_ATA` and attempt a pull to it. See [Core Concepts → Zero-Custody Architecture](/zero-custody) for why that matters and what S&A alone does and doesn't guarantee here.
